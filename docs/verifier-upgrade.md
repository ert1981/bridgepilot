# مسیر ارتقای تأیید پیام: از امضاکنندگان به اثبات رمزنگاری‌شده

> **وضعیت فعلی:** همه مسیرها با `MessageVerifier` (امضای آستانه‌ای) تأیید می‌شوند. BridgePilot **بریج مبتنی بر اعتماد به امضاکنندگان است** و تا زمانی که برای یک مسیر یک verifier رمزنگاری‌شده فعال **و** مستقلاً ممیزی نشده، نباید خود را trustless معرفی کند.

## ۱. معماری

```
BridgeVault / BridgeExecutor ──(immutable)──► VerifierRouter ──(برای هر شبکه مبدأ)──► IMessageVerifier فعال
                                                                                       ├─ MessageVerifier            (سطح ۱: امضای آستانه‌ای)
                                                                                       ├─ CompositeVerifier(A AND B) (سطح = بیشینه اجزا)
                                                                                       └─ verifier اثبات آینده       (سطح ۳: light client / ZK)
```

- `IMessageVerifier` مستقل از روش تأیید است: `verify(message, proof)`، `securityLevel()`، `verifierKind()`. قراردادهای بریج نمی‌دانند پیام چگونه تأیید می‌شود و `proof` برایشان مبهم است.
- سطح‌ها (آنچه برای جعل پیام لازم است): ۱ = تبانی `threshold` امضاکننده؛ ۲ = رزرو برای مدل خوش‌بینانه (امضاکنندگان + پنجره چالش بدون مجوز)؛ ۳ = شکستن سیستم اثبات یا اجماع شبکه مبدأ.
- `CompositeVerifier` ترکیب AND است: هر جزء باید بپذیرد، پس هیچ‌گاه از هیچ جزئی ضعیف‌تر نیست. گام مهاجرت پیشنهادی: `AND(امضاکنندگان, اثبات)` تا سیستم اثبات بالغ شود، سپس در صورت تصمیم، `اثبات` به‌تنهایی (هم‌سطح، پس مجاز).
- `VerifierRouter` با `USE_VERIFIER_ROUTER=true` (پیش‌فرض) در `script/Deploy.s.sol` مستقر می‌شود، پس ارتقا بدون جابه‌جایی وجوه ممکن است.

## ۲. قواعد ارتقا (در قرارداد اعمال می‌شوند، نه در سند)

| قاعده | پیاده‌سازی |
|---|---|
| **بدون کاهش سطح** | `proposeUpgrade` و `activateUpgrade` سطح جدید را با بیشینه (سطح فعال، کمینه مسیر) مقایسه می‌کنند؛ کمتر ← `Downgrade`. کمینه مسیر پس از هر فعال‌سازی بالا می‌رود (ratchet) و `raiseMinLevel` فقط افزایش می‌دهد. هیچ تابعی برای کاهش وجود ندارد. |
| **بدون جایگزینی بی‌سروصدا** | پس از `initRoute` (یک‌بار برای هر مسیر) verifier فعال فقط با پیشنهاد عمومی (رویداد) و پس از `upgradeDelay` ≥ **۷ روز** (ثابت `MIN_UPGRADE_DELAY`، در سازنده اعمال می‌شود) عوض می‌شود. |
| **همان چیزی که پیشنهاد شد** | هنگام فعال‌سازی، codehash و سطح اعلام‌شده دوباره خوانده می‌شوند و باید دقیقاً همان مقادیر پیشنهاد باشند. |
| **توقف اضطراری** | guardian (همان pauser) هر پیشنهاد معلق را در هر زمان وتو می‌کند و می‌تواند مسیر را روی قرارداد بریج متوقف کند؛ هیچ‌گاه نمی‌تواند چیزی پیشنهاد یا فعال کند. |
| **قابل ردیابی** | تاریخچه همه فعال‌سازی‌ها (آدرس، سطح، codehash، زمان) روی زنجیره (`historyAt`). |
| **بدون کاهش اضطراری** | اگر verifier فعال معیوب باشد، مسیر متوقف و مهاجرت می‌شود؛ هرگز به verifier ضعیف‌تر برنمی‌گردد. |
| **دفاع در هر فراخوانی** | `verify` اگر سطح اعلام‌شده verifier فعال پایین‌تر از کمینه مسیر برود، رد می‌کند. |

## ۳. نقش gate (`verify-deployment.ts`)

- قرارداد بریج باید روتر را به‌عنوان verifier داشته باشد؛ `upgradeDelay` ≥ ۷ روز؛ نقش‌ها: `DEFAULT_ADMIN` = {timelock} و `GUARDIAN` = {pauser}، با بازسازی کامل تاریخچه.
- برای هر مسیر: verifier فعال همان `activeVerifier` پیکربندی‌شده است، سطح ≥ کمینه ≥ ۱، و **codehash آن در `verifierPolicy.allowedCodeHashes`** (فقط پیاده‌سازی‌های ممیزی‌شده) است.
- پیشنهاد معلق در `operational` گزارش می‌شود؛ اگر codehash آن ممیزی‌شده نباشد، gate بسته می‌شود (ارسال رو به جلو متوقف، بازپرداخت ادامه) تا guardian وتو کند.

## ۴. محدودیت صریح

سطح امنیتی را خود verifier **اعلام** می‌کند. حاکمیت مخرب می‌تواند verifierی بسازد که درباره سطحش دروغ بگوید. قرارداد این را نمی‌تواند تشخیص دهد؛ دفاع‌ها: تأخیر عمومی ۷روزه، وتوی guardian، و allowlist کد ممیزی‌شده در gate. ratchet جلوی کاهش سطح **اعلام‌شده** را می‌گیرد، نه جلوی دروغ.

## ۵. relayer

`RelayerChain.proofBuilder(message, signatures)` آرگومان `proof` را برای verifier مقصد می‌سازد (پیش‌فرض: خود امضاها). پس از ارتقا به `CompositeVerifier`، prover در همین‌جا وصل می‌شود؛ بدون آن، انتقال به `RECOVERY_REQUIRED` می‌رود و هیچ وجهی جابه‌جا نمی‌شود (آزمون e2e «upgrade path»).

## ۶. نقشه راه برای هر خانواده شبکه (هر کدام پروژه جداگانه، با ممیزی مستقل)

| مسیر | روش اثبات پیشنهادی | پیش‌نیازها |
|---|---|---|
| L2 (OP Stack / Arbitrum) ← Ethereum | اثبات خروجی rollup روی L1 (state root از قرارداد خروجی/assertion نهایی‌شده) + اثبات Merkle-Patricia رویداد/storage | صبر تا پایان پنجره چالش یا fault proof فعال؛ هزینه گس اثبات storage |
| Ethereum ← L2 | خواندن state root ای که خود L2 از L1 دریافت می‌کند (پیام بومی L1→L2) + اثبات storage | پشتیبانی بومی هر L2؛ تأخیر |
| Ethereum ↔ زنجیره EVM مستقل | light client مبتنی بر sync committee (ZK برای کاهش گس) | prover، ممیزی مدار، مدیریت دوره‌های committee |
| L2 ↔ L2 | ترکیب دو مسیر بالا از طریق L1 | مجموع تأخیرها |

تا پایان هر ردیف و ممیزی آن، آن مسیر در سطح ۱ (امضاکنندگان) می‌ماند و مستندات و رابط کاربری باید همین را نشان دهند.
